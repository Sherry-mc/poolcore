# 池核 · POOLCORE

一个池核（Poolcore）爱好者的浏览站点：收录若干**程序化生成**的空旷泳池场景，
以第一视角 360° 环视，配实时合成的水声与回声，支持收藏、投稿自己的场景参数。

## 怎么打开

**方式一（推荐）：直接双击**

```
PoolcoreSite/index.html
```

站点不用任何构建步骤，也不用联网：所有画面由 Canvas 现场绘制，所有声音由 Web Audio 现场合成，
没有一张外部图片、没有一个音频文件、没有一次网络请求。

**方式二：本地静态服务器（推荐用于长期使用）**

部分浏览器在 `file://` 协议下会禁用或限制 `localStorage`（收藏与投稿就存不下来）。
如果发现收藏在刷新后丢失，用任意静态服务器打开即可正常持久化：

```sh
cd PoolcoreSite
python3 -m http.server 8000
# 然后浏览器打开 http://localhost:8000
```

## 光照

顶栏那条滑条改的是 **`cam.light`（0.3~1.5）**，渲染器在**出像素那一刻**整幅缩放：

```js
var er = or * exposure, eg = og * exposure, eb = ob * exposure;
data[pid] = er > 1 ? 255 : (er < 0 ? 0 : er * 255);
```

关键在「先乘再截断」：高光本来会被截到 1，先乘就能把过曝的部分救回来，
所以调暗不是「整幅变灰」，是**有层次地暗下去**（正午那种偏曝的场景尤其明显）。
代价是每像素 3 次乘法，实测 +0.6 ms（540p，约 1.3%）。

值存在 `poolcore:settings` 的 `light` 里，**画廊缩略图、首页主视觉、投稿预览也照它来**
（`P.store.lightLevel()`），免得出现「查看器里压暗了、缩略图还是亮的」。

## 水面

水的做法改过两轮。第一版照着实拍照片（Wikimedia Commons 上的清澈池水、池底焦散），
重点是**焦散光网**：细亮线织成不规则多边形格子。后来参考了一张「白瓷砖水道」的图，
那水的读感是 **几乎不上色的极透 + 大块柔和的白色反光 + 反光里的细皱褶**。

第三轮是**照着参考视频把波的主次理清**。参考（一间漫了薄水的白瓷砖房）里能看见的是
**一个个小波**：格子十几厘米到二十几厘米，起伏很浅，整片水像一层绷紧的纱，
云的倒影只在细处碎开 —— 不是一大块缓慢起伏的果冻（我中间走错过一次：
把「大起伏」的波长做大、坡度放大，渲出来就是果冻）。

所以现在两档波分工明确：

- **细纹（波数 `6.6/5.7/4.5`，格子约 0.25m）是主角**，水面看得见的「小波」全在这一层；
  它的反光项（`curl`）要加强，因为「一个个小波各自反光」才是那层细密亮格子的来源；
- **慢波（`2.2/1.9/1.5`，波长两三米）只管大镜面**（云的倒影整体慢慢摇），
  坡度压到 `×0.22`、位移系数 `0.05` —— 它一放大，整片水就开始像果冻；
- 细纹的**折射位移按水深给**（水深 2m、坡度 0.13 时横向错位约十几厘米），
  池底瓷砖的格子因此起细密的皱 —— 这是室内场景里「水在动」最直接的证据；
- **池底光网基本关掉**（`1 + caus × 0.8` → `× 0.22`，水面白分量 `0.05 → 0.015`）：
  参考的水面没有那种白色条纹，之前那一版那些大块白斑就是它。

**每个波有自己的方向。** 一池水的波不是一个朝向。中间试过「用一张平滑的风场把整池
拧着转」，结果整片水像一块果冻在晃 —— 太平滑、太「自然」，反而假。
现在就是老老实实叠若干个**驻波**，每个波自己一个方向：

按 **GPU Gems 1《Effective Water Simulation from Physical Models》** 那套
「正弦/郭士纳波之和」来。原文点名了几种失败，其中两条正是「水在往同一个方向来回晃」：

| 现象 | 成因 | 对策 |
| --- | --- | --- |
| **驻波：波节钉住、原地上下抖** | 出现反平行的同波长成对波，`sin(kx−ωt)+sin(kx+ωt)=2sin(kx)cos(ωt)` | 方向随机且**不互补** |
| **规则编织状格子** | 所有波在 t=0 相位都是 0，峰谷对齐在原点 | 每个波**独立随机相位** φ∈[0,2π) |
| **整块来回晃 / 像一块板在滑** | ω 与 k 无关（所有波一个速度） | **色散关系** ω=√(g·k)（原文称"不晃"的核心） |

于是每个波都是**行波**、带自己的方向与相位：

```js
// compile：三个尺度各一批波，方向按黄金角撒开，波长对数均匀取
sK[i] = TAU / (4.8 * pow(7.1/4.8, h1));   // 慢波 4.8~7.1 m
mK[i] = TAU / (1.1 * pow(2.8/1.1, h1));   // 中尺度 1.1~2.8 m ← 看得见的那层
fK[i] = TAU / (0.42 * pow(0.70/0.42, h1));// 细纹 0.42~0.70 m
sO[i] = sqrt(9.81 * sK[i]);               // 色散：短波自然抖得快
sPh[i] = h2 * TAU;                        // 随机相位

// 逐像素：sin(k·n·x − ωt + φ)，坡度也顺着它自己的方向 n
av = fsin((x*sCx[i] + z*sCz[i]) * sK[i] + sT[i]) * sA[i];   // sT[i] = φ−ωt，整帧算一次
slx += av * sCx[i];  slz += av * sCz[i];
```

**三层尺度**：慢波（4.8~7.1 m，只 0.1 档、轻轻揉一下倒影）+ 中尺度（1.1~2.8 m，
**水面和倒影的细节主要靠它**）+ 细纹（0.42~0.70 m，那层碎光）。
只靠长波是不行的：几条长波的相速度很接近，会叠成**一张整体漂移的大图案** ——
眼睛看到的就是「整片水朝一个方向来回晃」，小池里的水本来也不该是几条长涌。

振幅按 `Σa² ≈ 2.4` 归一（与老版总能量一致），`φ−ωt` 整帧算一次、逐像素只多一次加法。
种子由场景定死，同一场景每次打开完全一样。三层共 14 个波，代价 **约 +4.8 ms（6~8%）**。

**想改快慢只动一个数**：`js/core/renderer.js` 顶部的
`var WAVE_SPEED = 0.75;`（1 = 真实秒，0.75 ≈ 慢 25%）。
它只乘在时间上、不碰 ω，所以「短波快、长波慢」的色散关系不变 ——
等于把整池水一起放慢/加快，不会变成另一种水。
实测（同机位、隔 1 秒的平均变化）：原速 7.21 灰阶 → 0.55 档 5.40 灰阶 →
**0.75 档 8 灰阶上下**（0.55 时静止看几乎看不出水在动，才往上调的）。

### 让「停手之后水还在动」真的看得出来（2026-10-28）

以前静止时的水只有近处几米在动：中尺度波按距离淡出（7~16m 归零），
整池又只留 0.1 档慢波 —— 池子长 25m，于是大半池水面被压成一块不动的瓷砖地。
一走一退画面动了，人就以为「水要靠我走才会动」。这一轮：

| 改动 | 之前 | 现在 |
| --- | --- | --- |
| 中尺度距离淡出 | 7~16m | 10~26m |
| 细纹距离淡出 | 3~8m | 4~13m |
| 慢波占比 | `rp*0.1` | `rp*0.2` |
| 池底折射位移 | 0.20 | 0.38（约 5~6cm） |
| 光网（池底光斑）频率 | ω 0.17~0.26（周期 25~35s） | 0.32~0.46（12~18s） |
| 水下光斑强度 / 隔水看池底的光斑 | 0.35 / 0.1 | 0.75 / 0.34 |
| 水下滑动（砖缝游动） | `uwW*0.09` | `uwW*0.12` |
| 池底照度 | `LI*0.95` | `LI*0.86`（白瓷砖顶到 255 的地方少了，砖缝回来） |

另外**「水面动效」开关不再等于冻结**：开 = 流畅（闲置帧按实测自定，最高 60fps），
关 = 省电（闲置帧压到 ~7fps）—— 两档水都在动，停下脚步不会再变成一潭死水。

### 对标正版池核游戏（POOLS / Anemoiapolis）

抓了 POOLS（Tensori，Steam appid 2663530）的官方截图做参照，池核的水有三个特征：

1. **以倒影为主，池底几乎不参与** —— 水是暗色镜面，池底的瓷砖格子保持完整，
   只轻轻晃。之前把池底折射错位放到 13cm，瓷砖被拉成一片密集的波浪线
   （「浴帘」感），就是「太像真水、不像池核」的来源。现在收到 **约 3.5cm**。
2. **大而缓的光滑起伏**，不是密碎波 —— 反光是被大起伏拉成的柔条，不是一层麻点。
   中尺度层幅度 0.34 → **0.22**，细纹（碎光）0.2 → **0.12**。
3. 慢波只做极轻的底噪（0.1 档），动律交给中尺度那一层。

参数对照（`shadeWater`）：`ampF = 0.18`、中尺度 `0.22`、细纹 `0.12`、
镜面法线 `slx * 0.24`、慢波 `0.1`。

### 整池质感一致：按距离淡出细节

波定义在世界坐标里：近处是一道宽缓曲线，远处同一道波被透视压进几个像素，
位移就把池底拉成密集波浪线 —— 这就是「近处的水好看、远处的水花掉」的原因。
所以照瓷砖 mipmap 的办法给水面也做距离淡出：

- 细纹（0.42~0.70 m）：3 m 内全给，8 m 外为 0；
- 中尺度（1.1~2.8 m）：7 m 内全给，16 m 外为 0；
- 慢波（4.8~7.1 m）不淡出 —— 它二十米外也有上百像素宽，不会花。

淡出到 0 就**整段跳过**那几条波的计算（水面像素大多离得远，这正是开销大头）。
整池水从此是同一种质感。

### 闲置动画降内部分辨率（防卡）

闲置帧原来一直用全画质（540/720p），水一重就要 60~70ms，帧率掉到 10fps 左右。
现在闲置帧最高 450p（`viewer.js` 的 `idleQuality()`）—— 水在动，看不出柔一点，
帧时间省三成；静止补高清那条路不变，截图/细看仍是全画质。
实测（整帧）：540p 65.7ms → 450p **45.5~48.2ms**。

验证（`/tmp` 里的对照脚本）：

| 指标 | 旧（驻波 sin·cos） | 现在（行波+随机相位） |
| --- | --- | --- |
| 时间自相关峰（会不会"回到原样"地来回晃） | 0.35 / 0.31 | **0.24 / 0.24** |
| 两帧之间最佳平移（有没有整体漂） | — | **(0,0)，平移帮助 0%** |
| POD 第一模态能量占比 | 16~22% | 16~25% |

（自相关只能是"越接近 0 越好"：行波在一个周期后也会回到原样、只是位移了，
所以这个指标对"行波/驻波"只能部分区分；POD 对这段画面也不敏感 —— 可见内容被
镜面和瓷砖主导。真正能定性的还是三条判据本身的物理正确性。）

### 幅度与速度：对齐参考视频

参考视频（`桌面/录屏2026-10-10 18.28.13.mov`，白房间漫一层薄水）里是两档完全不同的节奏，
抽帧放大后量出来的：

| | 参考视频 | 做法 |
| --- | --- | --- |
| 大起伏 | 几秒一轮的**缓慢**宽起伏 | 慢波 4.8~7.1 m，周期约 2.0~2.6 s |
| 细碎反光 | **快速**明灭，间距约 10~25 cm | 细纹 0.42~0.70 m，周期约 0.5~0.7 s |
| 倒影 | 几乎是平的，云影「认得出」、只有边缘在慢慢摇 | 镜面法线只取慢波的 `slx * 0.24`，**细纹完全不参与** |

细纹只负责「水面那层细密反光」（⑤ 的 `curl`）——它在法线里进不去，
所以倒影干净、水面又是一层玻璃纱，两件事互不干扰。

### 反光不再朝一个方向爬

「反光一直在往一个方向动」的真凶是**池底光网**：原来那 4 束是朝固定方向漂的**行波**
（`fsin(bx*3.0 + tt*0.6)` 这种形式）。现在跟水面同一套做法 —— 4 束**驻波**、
各自一个方向（方向直接取细纹那批），于是光网是**原地明灭重排**。

客观验证（`/tmp/drift_ab` 同款思路，直接对光网场做平移检测，隔 3 秒）：

| 光网 | 最佳平移 | 平移能减少的差异 |
| --- | --- | --- |
| 旧：行波 | **(-2, +3) 格** | **62.0%** ← 确实在整体平移 |
| 现在：驻波 | **(0, 0)** | **0.0%** ← 原地重排 |

渲染出来的水面图案也测过：两帧之间最佳平移恒为 (0,0)、平移帮助为 0%。

实测（同机位、按 0.25 秒采样量帧间变化）：运动速率是原来「真水碎波」版的 **50~61%**，
但画面细碎度不降 —— 也就是「动得慢、纹路细」，正是参考的读感。

**最关键的一条是「一张面派生所有效果」。** 中间有一版折射、倒影抖动、细皱褶各用一套
互不相干的波，结果水看着像贴了一层贴图、不立体 —— 因为眼睛读到的是三层没有关系的图案。
现在只有一个波场（三束低频波 + 它们的三倍频谐波），坡度同时喂给下面每一层：

1. **折射**：池底被整张面推着晃（`0.13 × 水深`，大起伏和细纹都在位移里）——
   瓷砖的格子会轻轻游动，这是最直接的「有厚度」的暗示。收小过：原来是 0.3，
   那看着太像「真水」了。
2. **池底光网**：勉强留一层焦散。四束波叠加后的**过零线**就是亮线，格子疏密由
   `间距 ≈ π / 波数` 决定（不是单束波长）；实拍格子只有 0.2~0.3m，那个尺度在 500p 下会
   退化成噪点，所以取 0.8m 上下、线用平方收窄、强度只给四成。
3. **透**：水几乎不上色，池底看得清楚。吸收只跟「水有多深」有关：
   浅池接近玻璃，深池才慢慢压成一种颜色。
4. **真镜面**：把视线按波面法线**真的反射一次**，再拿它去打天花板取亮
   （`R = V − 2(V·n)n/|n|²`，取落点处的预烘焙光照）。倒影会被波面揉弯、掠射时自然
   拉成长条 —— **立体感主要来自这一层**：亮暗跟着同一张面的形状走。
5. **大面柔光 + 细皱褶**：白光片是**加**上去的（底下瓷砖照样看得见，不是把水色盖掉），
   皱褶用谐波那一档的坡度。菲涅尔（视线越平越强）在最后收尾，亮度量级提到
   「亮处 ≈ 1」，亮处直接过曝成白。

**运动**：又参考了一段「淹水的房间」视频（地板是一面近乎静止的镜子，云影完整地映在水里、
只做原地起伏）。照它改了三处：

- **基本波和细纹全部改成驻波**（正反两列等幅行波叠加，只留 2% 漂移）——
  行波会让整片图案朝一个方向平移，看着像「水在流」；驻波才是「水在原地起伏」。
  细纹也必须驻波：只让细纹漂的话，整片水看着还是在流动。
- **节奏对上视频**：驻波的呼吸周期从约 20 秒收到约 **1.2 秒**（视频里约 1 秒）。
  这个数是用「逐帧差分」量出来的 —— 拉一段 0~2 秒的时间序列，比较水面区域的变化量曲线：
  视频是先涨到 5 左右再回落的**周期**曲线，我们原来是**单调增长**的漂移曲线。
- **镜面用的坡度缩到 0.42 档**：反射距离有十几到几十米，用满幅坡度相当于把倒影平移十几米，
  倒影会彻底散掉、只剩波纹。缩下来之后倒影「认得出」、只是边缘在慢慢摇 —— 那才是镜面感。

另外，查看器的空闲动画改成了 **requestAnimationFrame 自己计时**（原来用 `setInterval`）：
浏览器对定时器有节流（窗口被遮挡、后台、省电模式），被掐掉就会表现为
「动一两秒然后不动了」；rAF 只在页面真的不可见时才停。

**空闲动画的帧率**：原来固定 130ms（7.5fps），在「1.2 秒一个起伏」的水面上只有 9 帧，
看着就是一跳一跳的。现在两处改了：

- **只重画真的有水的行**：渲染器每帧顺手记下哪些行画到了水（`stats.wy0/wy1`），
  空闲动画就只重画这一段（上下留 2 行余量），比一律重画下半屏省一截；
- **按实耗自适应**：每帧画完都知道自己花了多少毫秒，下一帧的间隔取
  `实耗 × 1.18 + 4`，夹在 33~110ms 之间 —— 快机器往 30fps 顶，慢机器自动退。

实测（儿童池，无独显）：水面那半屏一帧要 **34ms（540p）/ 60ms（720p）**，其中
**水面着色占 77%**，逐项拆开是「反射贴图 3.7ms + 池底光网 3.6ms + 两次除法 3.5ms +
池底光照 1.5ms + 细纹 1.8ms + 其余（混合/菲涅尔/位移）约 10ms」—— 没有单点大头，
就是每个水面像素要算 60~80 个操作。所以这台机器上 720p 的空闲动画上限约 15fps、
540p 约 25fps；想更滑就把画质调到 540p。

「亮」还跟着场景的天光 / 灯走（`water.sheen = 0.24 + 天光×0.4 + 强度×0.26`）：
夜里几乎不反光，户外正午最亮 —— 不然夜景会糊上一层白。

整条水面路径全是查表正弦加两次除法，没有贴图；两轮改下来单帧耗时基本没变
（540p 下儿童池 36.8 → 37.1ms）。

光网的白分量是加在**水色之后**的（深池里池底几乎看不见，光网却照样亮）。
它的**颜色跟着那束光走**：默认偏白青（清水里就是这样），暖光场景可以写
`water.caustic` 换成金色 —— 「户外池 · 黄昏」就是暖琥珀水色（`#8A5A22`）+
金色光网（`#FFD9A0`）；冷薄荷青的水配暖瓷砖会很别扭。

**砖缝是近黑的**：`pal.grout` 定在亮度 0.055（只留一点场景色相 —— 蓝池是黑蓝、
暖池是黑棕），场景里的 `tile.grout` 也整体加粗了一档；天花板那片离眼睛近，
再压黑会发脏，所以它的缝用深灰 0.3。

缝在屏幕上的宽度会随距离变细，这里不能只做「细了就加宽」—— 那在远景会断成一串
虚点（点阵 = 网格在像素栅格上的摩尔纹，黑缝尤其难看）。所以两种机制合成一层：

- 缝宽 ≥ 1 像素：**盒式一维抗锯齿画实线**（距缝中心半像素以内吃满）；
- 缝细到亚像素：不画线，改成**整块砖按缝占的面积均匀压暗**（面积平均），
  平得干净、不会有点阵。

两者都朝同一个缝色混，所以能合成一个标量，逐像素只查一次 9 档的预混表
（档位做到 9 档，是因为面积平均那点暗度只有 0.1 上下，5 档取不准）。

## 天空与太阳

屋顶那个洞以前只是「亮一点的顶」—— 一块被冲淡的雾色。现在它是**洞**：洞里看见的是
天空本身，而且整块天空都是按**方向**现算的（没有贴图、没有预烘焙）。于是
「天窗里看到的那块天」和「水面倒影里的那块天」是同一份东西，**水面上的亮斑因此永远
落在太阳那一侧**，而不是「天花板上那块亮」。

天空由四样东西叠出来（`shadeSky`，输入只有一条单位方向）：

1. **梯度**：天顶色 → 地平线色，仰角开方以后过渡更薄；
2. **云带**：三层值噪声，横向按方位铺、纵向按仰角拉长，所以是一层层横条；
   值噪声本身很「软」，先拉对比再切，云才有形状；
3. **太阳盘 + 暖晕**：和太阳的夹角余弦派生出盘、内晕、外晕；盘过曝成白，
   嫌刺眼就用顶栏那条光照滑条压；
4. **云的金边**：云自己的颜色按「离太阳多近」在两色之间插值 —— 朝阳侧金，
   背光侧暗糖色。

**性能**：天空逐像素算，所以云场预表一次（104×34，建一次），逐像素只做双线性。
全屏天空（仰头看洞口）从 +22 ms 降到 **+11 ms**；水面倒影取天空 **+5 ms**。

**洞口与倒影共用一个判据**：`skyAt(x, z)` 给出「这个屋顶上的点在洞里有多深」，
天花板用它决定「露出天空还是屋顶」，水面倒影用它决定「取天空还是取天花板反光贴图」。

**太阳也给方向光**：朝着太阳那面墙亮一档（`shadeWall` 里按 wallId 与太阳水平分量点乘）。

场景可以写 `sky: { top, horizon, cloud, cloudLit, sun, az, el, bright, cover, sunPow, sunI }`
覆盖；不写就按雾色 + 天窗强度自动推（所以「天窗开得越大，天越亮；夜里几乎是黑的」）。
`az` 是从 -Z 起朝 +X 转的角度，`el` 是仰角 —— 太阳得抬得够高，才能从屋顶洞里露出来。
「户外池 · 黄昏」给了整套日落配色（暖橘瓷砖 + `el: 24` 的太阳 + 压暗的云），
两个夜景则显式给了暗夜空。

坑记两个（都是 `var` 提升的坑，写代码时容易再踩）：
`buildCloud()` 必须放在 `CLW/CLH/cloudTab` 的**赋值之后**调用 —— 写在前面的话
循环条件拿到 `undefined`，表是空的（云整片消失，而且不报错）。
另外水面倒影那段里 `glow` 必须在 `if/else` **两条分支上都有值**，
少一条分支 `spec` 就是 `NaN`，画出来是一块块黑斑。

## 深水：按通道吸水

`water.absorb`（默认 0 = 老行为）打开按通道的水体吸收：光在水里不是均匀变暗，
**红光最先没**，蓝绿穿得深（清澈池水约 0.34 / 0.10 / 0.055 每米，再乘上 absorb）。
三处用到它：

1. **透过率**：看池底时按 `exp(-a · path)` 逐通道衰减，而不是一个标量可见度 ——
   所以深水里先没的是红，池底沉成墨绿直到黑，而不是「整片糊上一层水色」。
2. **池底照度**：光要穿 `水深` 米才到池底，所以池底只剩 `exp(-a · 水深)` 那点亮度
   （回程那一半已经算在视线里）。9.6m 的池底实测只剩 **2/255** —— 这就是「不见底」。
3. **水下墙面**：水位以下的墙面隔着水看，按视线在水里的长度衰减 —— 深池里下半截会黑下去，
   而不是像在空气里那样亮着。

「深水池 · 不见底」的参数：`bottom: 9.6`、`absorb: 1.6`、水色 `#04141C`、
`sheen: 0.3`（把大面柔光压掉，水才像黑玻璃）、只留两道灯 ——
水面上那两条亮痕就是它们，也是这张画里唯一说得出「这是水」的东西。
「深水区 · 五米」也按名字给了 `bottom: 4.8`：跳水池本来就是另一个池子。

## 道具（蘑菇伞 / 滑梯）

`props` 是可选字段，池子里能放两样东西。它们在渲染器里是一组**解析基本体**
（竖圆柱 / 椭球顶 / 平行四边形），跟射线直接用一元二次方程求交 —— 没有网格、没有贴图：

```js
props: [
  // 蘑菇伞：立柱 + 伞面（上半椭球 + 平的伞底），伞底在地上投一圈阴影
  { type: 'mushroom', x: -1.7, z: -0.4,     // 世界坐标，米，原点在大厅中心
    capR: 1.15,                             // 伞面半径
    capY: 2.02,                             // 伞沿高度
    capH: 0.4,                              // 伞面高 / 半径（越大越鼓）
    color: '#D9574E', stemColor: '#EDEDE6',
    base: 'pool',                           // pool = 站在池底（默认）／deck = 站在池沿
    curtain: true, streams: 9,              // 从伞沿垂下一圈水帘（戏水池那种）
    shade: 0.5 },                           // 伞下阴影强度 0~1
  // 滑梯：滑道 + 两侧挡板 + 平台 + 梯子（两杆三档）+ 两根支撑杆
  { type: 'slide', x: 6, z: 1.5,
    rot: -90,                               // 下滑方向的水平角（度）：局部 +Z 就是下滑方向
    h: 1.3,                                 // 平台高度
    len: 2.4,                               // 滑道长度
    w: 0.62,                                // 滑道宽度
    color: '#E8B23A' }
]
```

`x / z` 会被夹在大厅内（留 0.45m 边距）；落在池子里就是站在水里，落在池外就是站在池沿上。
有道具的场景会在信息抽屉里多出「蘑菇伞」「滑梯」两个热区，点一下镜头平滑转过去。

**开销**：每帧先按包围圆柱做一次逐列预筛，逐像素只在「射线可能碰到的那几列」里精确求交。
「蘑菇伞 + 滑梯」大约多 10% 单帧耗时；没有 `props` 的场景一分钱不花。

沉在水下的那截（立柱、支撑杆）也会画出来，按水色压暗一层近似「透过水看」，不会硬切在水面上。

## 池子几何：盆底固定，深浅交给水位

所有池子共用**同一个标准盆底** `POOL_BOTTOM = 2.2 m`（`js/core/renderer.js`），
场景里不再写 `pool.depth`（写了也会被忽略）。于是「同一个池子、不同的水量」：
池底永远在 -2.2 m，水多水少由 `water.level` 说。抽干的场景把水位压到盆底以下即可
（`废弃池 · 已排干` 就是 `level: -2.6`）。

只有**儿童池 / 戏水池是另一个池子**，用 `pool.bottom` 把盆底抬高
（儿童池 0.62 m、戏水池 0.66 m），那里才是真的浅。

投稿页的滑条也照这个改了：原来的「池深」换成**水位**（-2.6 ~ +0.45），
产出的数据里同样没有 `pool.depth`。

## 瓷砖

**默认是「干净到失真的白」**：逐砖明暗差 `tile.vary` 默认 **0**、污渍 `scene.dirt`
默认 **0** —— 一块块砖亮度完全一致，只有砖缝画出网格。这是这套画面的底色：
一旦白瓷砖里混进灰黑色的砖，那种「假得对味」的感觉立刻没了。
想要旧砖 / 水渍感，就在某个场景里主动打开：`dirt: 0.4`（成片水渍）、
`tile: { vary: 0.14 }`（逐砖明暗差）。`dirtAt()` 是粗格值噪声双线性插值，
脏出来是成片的形状、边缘平滑过渡；墙上把格子竖着拉长（1.5 × 3.4 m）就变成顺墙淌的水渍。

另外两件事让近看 / 远看都站得住：
1. **池内壁必须用真实高度**。渲染池内壁时以前把 y 夹成了常数 0.02，
   于是整面墙的砖行坐标恒定、只有横向变化 —— 画出来是一道道竖条纹，
   而且水位线那圈印子也一起丢了。现在传真实 y。
2. **手工 mipmap**。一块砖在屏幕上不足几像素时，砖缝与逐砖噪声会退化成摩尔纹
   （远景像撒了沙）。所以按「砖在屏幕上还剩几像素」把细节淡掉：竖直方向看地面 /
   天花板是 `1/距离²` 掉的，横向看墙是 `1/距离 × 墙走向与屏幕的夹角余弦`，
   取更扁的那个。砖缝另做一遍抗锯齿 —— **不足一像素就把缝加宽到一像素、颜色按
   覆盖率变淡**（总墨量不变），这样远景是连续细线而不是一串点。
   全部新增计算实测只多 **0~1.5%**（`bench_tile.js`）。

## 投影

严格的针孔投影：每像素的射线是 `dir = 前·f + 右·ax + 上·ay`，`f = (H/2) / tan(fov/2)`，
`ax`、`ay` 是横纵像素坐标归一化到 `[-1,1]` 之后再乘 `W/2`、`H/2`。

**横纵必须用同一个像素尺度。** 这里曾经在 `ax` 上多乘过一个 2：等于把画面水平拉伸两倍、
还把光轴推到了 1/4 宽处（正方形瓷砖在屏幕上会变成 2:1 的宽矩形，一动镜头整个房间都在变形）。
修掉之后水平视场才是正常的 —— vFOV 62° 配 1.9 的宽高比约等于 hFOV 99°。

## 性能

画面是逐像素算出来的，所以**分辨率就是唯一的开关**。同一视角下实测（Chromium / V8，
`室内池·儿童池`，无独显），耗时与像素数几乎完全成正比、没有固定开销：

| 内部高度 | 像素 | 单帧耗时 | 每像素 |
| --- | --- | --- | --- |
| 360p | 700 × 360 | ≈ 12.4 ms | 49 ns |
| 540p | 1051 × 540 | ≈ 27.1 ms | 48 ns |
| 720p | 1401 × 720 | ≈ 47.5 ms | 47 ns |

即 `耗时 ≈ 4.7e-5 ms × 像素数`。水面占屏大的视角仍更贵（约 70 ns/像素）。
（改写水面着色前同一视角是 16.7 / 36.2 / 66.7 ms —— 新版水面的正弦次数更少，反而快了约 28%。）

**注意屏幕缩放**：在 2× 屏上，画布 CSS 高 753 意味着物理 1506 像素 —— 内部 720p 已经被
放大 2.09 倍。要「物理像素级锐利」得内部 1500p 上下，那是 4 倍像素、不可能实时。
所以「清晰到跟原生一样」在 CPU 光栅下没有解，能做的只是别把分辨率压得更低。

交互时分辨率不是写死的，而是**每台机器自己找**：

- 高清帧（打开场景、松手、切换画质）画完会记下它花了多少毫秒；
- 因为「像素数 ∝ 分辨率²」，按 `√(预算 ÷ 实耗)` 反算，于是
  **下一帧一开口拖动就已经是对的分辨率**；
- 拖动过程中继续按实耗微调（单帧幅度夹在 ±30% 内、留有 8% 死区，不会来回抖）；
- 停手后补一帧所选画质：鼠标 / 触摸 190 ms，方向键 320 ms
  （要大于连按间隔，否则会和降分辨率来回翻，比糊更难受）。

预算 `DRAG_TARGET_MS` 现在是 **50 ms/帧（≈20fps）：画质优先**。这让重场景（儿童池）拖动时
落在 500~520p 上下，而不是早先写死的 240p；便宜的场景直接给满所选画质。
想更跟手就把它调小（如 30 → ≈26fps、但更软），想更锐就调大（如 70 → ≈14fps）。

停手后的水面动画只在所选画质下重画下半屏（7.5fps），天花板与墙不重算。
不想让它动，就在信息抽屉里把「水面动效」关掉；系统开了「减少动态」时会自动关闭。

## 技术约定（重要）

为了让「双击即看」成立，整个站点运行在 `file://` 协议下，因此刻意遵守以下约束：

- 不用 `<script type="module">` / `import`：`file://` 下会被 CORS 拦截；
- 不用 `fetch` / `XMLHttpRequest`：读不到本地 json、图片、音频；
- 场景数据写成 `.js` 并挂在全局 `POOLCORE` 命名空间上；
- 脚本用传统 `<script src>` 按固定顺序引入（数据 → 渲染 → 音频 → 存储 → UI → 装配），
  新增脚本时必须追加在依赖之后。

## 新增一个场景

只需要在 `js/data/scenes.js` 的数组里追加一条数据，渲染器与音景引擎都以它为唯一输入，
不用改渲染代码：

```js
{
  id: 'my-pool',
  name: '我的池',
  category: 'indoor',            // indoor | outdoor | night | abandoned
  tags: ['瓷砖', '回声'],
  desc: '一句话描述。',
  seed: 20261,                   // 决定细节分布的随机种子
  room:  { w: 22, d: 14, h: 4.6 },
  pool:  { insetX: 3, insetZ: 4.2 },          // 池子只有大小与位置，盆底是固定的
  // 只有儿童池 / 戏水池这种「另一个池子」才写 pool: { ..., bottom: 0.62 } 把盆底抬高
  water: { level: -0.18, color: '#2FA3C7', clarity: 0.7, ripple: 0.4 },
  // level 是水位（水面相对池沿的高度）：-0.18=正常水面，>=0=大厅进水（整间淹掉）
  // stain 可选：水位线那圈水碱印子的高度，抽干之后印子还留在墙上（不填就跟着 level）
  // level 低于盆底 = 完全抽干的池子，此时直接画池底
  // absorb 可选：按通道的水体吸收强度（0=关，1 约等于清澈池水），深水池靠它把池底吃成黑的
  // sheen 可选：直接指定水面大面柔光的强度（不填就按天光 / 灯自动推）
  tile:  { size: 0.25, hue: 196, sat: 0.35, light: 0.78, grout: 0.09 },
  light: { intensity: 1.0, hue: 38, skylight: 0.7, fixtures: 4 },
  fog:   { color: '#0B2A33', near: 4, far: 26, density: 1 },
  camera:{ height: 1.66, yaw: 180, pitch: -7 },
  audio: 'indoor-hall',          // indoor-hall | outdoor-open | night-hum | abandoned-drip
  props: [                       // 可选：池子里的道具（见下）
    { type: 'mushroom', x: -1.7, z: -0.4, capR: 1.15, capY: 2.02, color: '#D9574E' },
    { type: 'slide', x: 6, z: 1.5, rot: -90, h: 1.3, len: 2.4, color: '#E8B23A' }
  ]
}
```

也可以直接在「提交场景」页里拖滑块调参，实时预览满意后复制/下载 JSON，
把生成的那条数据粘回 `scenes.js` 就能收录进画廊。
